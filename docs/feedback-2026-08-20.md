## B. Bug found in their own screenshot — wrong RM/kg

Not something they flagged; found while reading the Quote Comparison
screenshot. It is the same class of wrong-money bug as the ones already fixed.

RFQ `6061 PLATE; ref: SO26-08453 (5)(6)`, supplier BXXX Sdn Bhd:

| Item | Entered as | Qty | RM/pc |
|---|---|---|---|
| 1 · ALU 6061 PLATE | (3.00) x (122.00) x (122.00) | 200 | 22.50 |
| 2 · ALU 6061 ROD | (127.00) x **0.00** x (36.00) | 100 | 15.30 |

The rod's diameter went in the Thickness field with Height left at `0.00`, and
no `Ø` was used. So the app multiplied `127 x 0 x 36` and got **zero weight**,
while the rod's RM 1,530 still counted toward the total:

| | App showed | Should be |
|---|---|---|
| Total RM | 6,030.00 | 6,030.00 |
| Total kg | 24.112 | 153.451 |
| **RM / kg** | **250.08** | **39.30** |

**RM/kg overstated 6.4x.** RM 250/kg for aluminium is obviously wrong to anyone
in the trade, but the number is presented with no warning. Both figures above
reproduce the screenshot exactly, so this is confirmed, not theoretical.

Root cause: `pieceWeightKg()` returns `0` for a zero dimension, not `null`, so
the existing "weight incomplete" guard never fires. Two fixes needed:
1. Treat a zero or missing dimension as *not weighable* (null), which suppresses
   RM/kg and flags it, rather than silently contributing 0 kg.
2. Help the user enter rods correctly — if the material says ROD/BAR/SHAFT and
   no `Ø` is present, prompt for it.

Also cosmetic: the email prints `ALU 6061 ROD-127.00 X 0.00 X 36.00`, showing a
meaningless `0.00` to the supplier. Blank dimensions should be omitted.
